Case study · Testing harness

gyro-bench

Eight behavioural suites against a local AI server: 49 cases, 44 OK, 0 failures and 5 informational.

Dependency-free Python speaking the OpenAI API against a live server. It tests behaviour, not speed: for speed there is xestrata --bench. With --seed 7 --repeat 3 the 16 thinking tasks repeated the same answer, so pass@3 measures model correctness rather than sampling noise. The report records what came out, not a "stabilised" answer.

How the numbers are obtained

Two sources per case: the response and the engine

The response carries per-request timings and does not require reading the log. /metrics adds what is global to the engine.

POST /v1/chat/completions   usage: prompt_tokens, completion_tokens,
                            completion_tokens_details.reasoning_tokens
                          timings: cache_n, prompt_ms, predicted_ms,
                                   prompt_per_second, predicted_per_second,
                                   draft_n, draft_n_accepted
GET  /health                supported thinking levels (default high)
GET  /metrics               expert hit_rate, ram_blobs, file_mb, reused,
                            loop_guard counters and hardware state
                            (?requests=all reads the whole 500-record buffer)
  • queue_ms is wall_ms minus engine time (prompt_ms + predicted_ms): how long the request waited behind other generations. If the queue is below --queue-tolerance (60 ms by default) the TTFT is marked clean with ttft_clean: true.
  • Pairing asks /metrics?requests=all (the normal view shows the last 12 records and the buffer keeps 500) and looks for the record whose time falls in the case's started..finished window with the same prompt_total and output_tokens. The one nearest to the start wins; the outcome is stored as engine_matched.
  • Tools go in the nested OpenAI format ({type: "function", function: {...}}). A 400 with an explicit body is a malformed payload from the harness, not an engine failure, and is not retried.
  • --from-results rewrites the report only from the saved results.json: snapshot_start and snapshot_end hold the run's /health and /metrics, so it does not touch the server.
  • A warm-up request goes first and stays out of the medians: its TTFT includes the cold loading of experts.

How to read the numbers

Five usual traps of these metrics

  1. 01

    Engine decode is not wall clock

    decode_tok_s is the engine's rate after accepted drafts. decode_tok_s_wall uses the real request clock and is much lower because it includes prefill and TTFT.

  2. 02

    The queue contaminates TTFT

    With a high queue_ms that TTFT measures waiting behind other generations, not model latency. In this run 24 of the 28 graded requests have a queue below 60 ms and their TTFT is reliable; the other 4 (the concurrent ones at n=4) waited 2,460–8,198 ms and stay marked with ttft_clean: false. The engine's tok/s are not contaminated.

  3. 03

    Prefill and cache contradict each other

    A high prefill rate with high cache_reused means the cache hit, not fast compute. The figure that matters there is TTFT.

  4. 04

    Informational is not a pass

    The scale n=2 and scale n=4 cases leave passed as None: concurrent scaling is an engine property (batch_slots: 0), not an exam of the model. Same for the warm-up request and the two none level traps, which carry expected_fail: true.

  5. 05

    pass@k with a seed, not an average

    With --seed the repetitions of a task are identical, so pass@3 measures model correctness rather than sampling noise. Without a seed, a medium level that passes today can fail in the next run.

python3 bench.py --quick                        # compact suite, ~2 min
python3 bench.py --seed 7 --repeat 3            # comparable run: pass@3 and determinism
python3 bench.py --suite tools,thinking,structured
python3 bench.py --long-tokens 24000            # more aggressive long context
python3 bench.py --json-out runs/1.json --report runs/1.md
python3 bench.py --from-results runs/1.json --report runs/1.md   # rewrite without touching the server

Run it with the server free. If another heavy session is using the same server, the concurrency numbers, expert hit rate and TTFTs suffer: this run was launched with the agent quiet and still 4 requests ended up queued.

Portable and engine-specific

What works with any server and what only works with this engine

Portable (any OpenAI-compatible API)

  • Verdicts for thinking, tools, structured, long_context and stability are decided by the response: content, finish_reason, tool calls and JSON.
  • Retries only on transient statuses; a 400 with an explicit body is treated as a malformed payload of the harness itself.
  • Without the timings block the tok/s stay None, but pass or fail still works.

XeStrata/Strata specific

  • hit_rate of experts, ram_blobs and file_mb: they only exist in this engine's /metrics.
  • loop_guard counters and thinking closure.
  • Hardware during generation: VRAM used, temperature, power and disk reads during prefill.
  • batch_slots and the reasoning_effort levels advertised by /health.

Harness fixes

Ten fixes already applied in this version

None of them changes the cases: they change how numbers are attributed and stored. All of them are in the version used for this run.

  • Pairing over the started..finished window on the whole buffer (/metrics?requests=all), requiring prompt_total and output_tokens to match: all 47 requests ended up joined (engine_matched).
  • results.json stores snapshot_start and snapshot_end of /health and /metrics, so --from-results rewrites the report without touching a live server.
  • TTFT is marked clean or contaminated according to --queue-tolerance, and the medians use only the clean ones.
  • The none level traps are expected-fail (passed: null, expected_fail: true): a fact about the model, not a harness failure.
  • The needle is placed at the start, the middle and the end of the long context: three cases, with VRAM, temperature, power and GGUF reads per case.
  • structured goes through run_case, so it has prompt_tokens, wall and an engine record.
  • --seed and --repeat give pass@k and determinism across repetitions.
  • pcie_share, prompt_read, projection, duration_s, decode_ms, reasoning_recoveries and file_blobs are collected, which /metrics already gave and were discarded.
  • A warm-up request goes first, informational and outside the medians.
  • The docstring names the real suites (thinking, not think) and documents the new flags.

What remains belongs to the engine, not the harness: a request id in each /metrics record would make pairing exact without relying on counters and timestamps.

Limits

What this suite does not prove

Caveats of the 14 Nov 2026 run

  • It was launched with the agent quiet: 24 of the 28 graded requests have a queue below 60 ms and their TTFT is reliable. The other 4 waited 2,460–8,198 ms behind other generations and stay marked; the engine's tok/s are not contaminated.
  • seed 7 and 3 repetitions per thinking task: the 16 repeated the same answer. Across runs without a seed, thinking changes.
  • Pairing uses a time window and counters because the server does not expose request ids; in this run all 47 requests were joined.
  • /metrics shows the last 12 records and its buffer keeps 500: the harness asks for requests=all.
  • batch_slots: 0 in the engine: concurrency only gains 1.06–1.22×, and the scale cases are informational.
  • Only one quantization (TQ1_0) and one card were tested; none of this is sustained or multi-user throughput.
