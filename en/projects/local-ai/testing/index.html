gyro-bench

Eight behavioural suites against a local AI server: 46 cases, 42 OK, 2 failures and 2 informational.

Dependency-free Python speaking the OpenAI API against a live server. It tests behaviour, not speed: for speed there is xestrata --bench. The thinking cases are not deterministic and the report records what came out, not a "stabilised" answer.

How the numbers are obtained

Two sources per case: the response and the engine

The response carries per-request timings and does not require reading the log. /metrics adds what is global to the engine.

POST /v1/chat/completions   usage: prompt_tokens, completion_tokens,
                            completion_tokens_details.reasoning_tokens
                          timings: cache_n, prompt_ms, predicted_ms,
                                   prompt_per_second, predicted_per_second,
                                   draft_n, draft_n_accepted
GET  /health                supported thinking levels (default high)
GET  /metrics               expert hit_rate, ram_blobs, file_mb, reused,
                            loop_guard counters and hardware state
  • queue_ms is wall_ms minus engine time (prompt_ms + predicted_ms): how long the request waited behind other generations.
  • Pairing looks in the rolling window for the record with the case's prompt_total and output_tokens.
  • Tools go in the nested OpenAI format ({type: "function", function: {...}}). A 400 with an explicit body is a malformed payload from the harness, not an engine failure, and is not retried.
  • --from-results rewrites the report from a saved results.json, but it queries the live server and shows its current counters, not those of the saved run.

How to read the numbers

Four usual traps of these metrics

  1. 01

    Engine decode is not wall clock

    decode_tok_s is the engine's rate after accepted drafts. decode_tok_s_wall uses the real request clock and is much lower because it includes prefill and TTFT.

  2. 02

    The queue contaminates TTFT

    With a high queue_ms, that TTFT measures waiting behind other generations. The engine's tok/s remain valid; the TTFT does not.

  3. 03

    Prefill and cache contradict each other

    A high prefill rate with high cache_reused means the cache hit, not fast compute. The figure that matters there is TTFT.

  4. 04

    Informational is not a pass

    The scale n=2 and scale n=4 cases leave passed as None: concurrent scaling is an engine property (batch_slots: 0), not an exam of the model.

python3 bench.py --quick                        # compact suite, ~2 min
python3 bench.py                                # full suite
python3 bench.py --suite tools,thinking,structured
python3 bench.py --long-tokens 24000            # more aggressive long context
python3 bench.py --json-out runs/1.json --report runs/1.md

Run it with the server free. If another heavy session is using the same server, the concurrency numbers, expert hit rate and TTFTs suffer.

Portable and engine-specific

What works with any server and what only works with this engine

Portable (any OpenAI-compatible API)

  • Verdicts for thinking, tools, structured, long_context and stability are decided by the response: content, finish_reason, tool calls and JSON.
  • Retries only on transient statuses; a 400 with an explicit body is treated as a malformed payload of the harness itself.
  • Without the timings block the tok/s stay None, but pass or fail still works.

XeStrata/Strata specific

  • hit_rate of experts, ram_blobs and file_mb: they only exist in this engine's /metrics.
  • loop_guard counters and thinking closure.
  • Hardware during generation: VRAM used, temperature, power and disk reads during prefill.
  • batch_slots and the reasoning_effort levels advertised by /health.

Planned fixes

Ten changes that make the numbers more defensible

None of them changes the cases: they change how numbers are attributed and stored.

  • Pair by request id instead of (prompt_total, output_tokens), so two cases with the same signature do not receive the wrong record.
  • Store a copy of /health and /metrics taken at the start and end of the run in results.json, so the report does not depend on a live server.
  • Mark clean TTFTs with a flag and exclude queue-contaminated ones from medians.
  • Turn the none level traps into expected-fail: they are a model fact, not a harness failure.
  • Place the needle also in the middle and at the end of the long context, not only at the start.
  • Make structured go through run_case so it gets prompt_tokens, TTFT and wall.
  • Fix a seed and measure pass@3 so runs can be compared.
  • Collect pcie_share, prompt_read, projection, decode_ms, duration_s and reasoning_recoveries, which /metrics already gives and are currently discarded.
  • Warm the server with one request before measuring and check in live.state that it is idle.
  • Fix the docstring: suite names are the real ones (thinking, not think).

Limits

What this suite does not prove

Caveats of the 14 Nov 2026 run

  • It ran while the same server was serving a coding agent: six requests waited 2,807–116,147 ms in queue, so their TTFT and wall stay contaminated.
  • Pairing with /metrics uses (prompt_total, output_tokens); duplicate signatures can attribute the wrong record.
  • /metrics keeps a rolling window of requests, not the complete history of the run.
  • Thinking cases are not deterministic: none failed the bat-and-ball and the trains problem in this run and may get them right in another.
  • Only one quantization (TQ1_0) and one card were tested; none of this is sustained or multi-user throughput.
