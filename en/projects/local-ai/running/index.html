Running local AI

XeStrata running qwen3.8-flash-next-gyro-gyro-s (GGUF TQ1_0, 54.5 GiB) on a desktop PC: 24 GB of VRAM and 32 GB of RAM. The real requirements, the quantizations you can choose, the four ways to install it, and what happens during the first start.

The start timings come from the engine log (11 November 2026) and the live server state comes from /metrics. The engine, the weights and the loop guard belong to other projects; what is mine here is the deployment and the measurements.

What was set by hand on this PC
The engine chose nearly everything itself from what it measured: --expert-cache auto and --prefill auto. What was fixed by hand was the context (--max-context 131072), the KV (int8), the VRAM reserve (--vram-reserve-mib 2048) and how the prefill is shared with the CPU (--prefill-cpu-share 0.79).
The PCIe link
Gen4 x8. The engine probes the link at start: 13.2 GB/s host to device (best of 12.4, 13.2, 12.5, 12.6), and set pcie_frac to 0.36 in that start; the server used for the tests reports 0.38.
A CPU without AVX-512
This is the case XeStrata documents as “no CPU matrix”: the experts are resolved in AVX2 with multi-token for the gate/up rows. It works, but the prefill of the experts that are not on the card is slower than on a CPU with AVX-512.

Installation

Four ways to put it in place

The package route is the simplest, but it only covers Ubuntu 26.04 and Fedora 44. On Ubuntu 24.04 what is left is the Podman container or the source, and that is the one used here.

deb / rpm

A package from GitHub Releases with SHA256SUMS: xestrata-contrib-cuda13.1 (Ubuntu 26.04) or xestrata-contrib-cuda13.4 (Fedora 44), and cuda12.4 for Pascal and Volta. Verified with sha256sum -c SHA256SUMS --ignore-missing, installed with sudo apt install ./<file>.deb, then xestrata --setup asks for model, context and images.

It does not work on Ubuntu 24.04. The free-software-only package (xestrata-free) is not in Releases: it is built with tools/package/build.sh ubuntu26.04 free.

Podman

A rootless Fedora 44 container: on the host you only need podman and podman-compose, plus the GPU driver and the user in the render group. podman compose build, podman compose run --rm xestrata --setup, podman compose up -d and the server on 127.0.0.1:8095.

Settings, logs and models are the host's, in the same places the packages use, so the two routes replace each other. For NVIDIA you need the CDI of the NVIDIA Container Toolkit.

Windows

XeStrata-<version>-windows-x64.7z unpacked into a folder: xestrata.exe guides the start on screen and xestrata-cli.exe is the console. It needs the .NET 10 runtime, the Visual C++ Redistributable and the GPU driver.

Settings go to %APPDATA%\\xestrata, logs and the rest to %LOCALAPPDATA%\\xestrata. Not tested in this project: it is documented, not measured.

From the source

./setup.sh: checks the GPU, RAM and CPU, chooses the SYCL compiler, builds the engine and downloads the model. It installs no system packages and uses no sudo, except Python if there is none; ./setup.sh --packages prints the line this distribution and these GPUs need.

Used here: contrib-llvm mode with intel/llvm 7.2.0 built by tools/intel_llvm_build.py, intel-oneapi-mkl-sycl-devel 2026.2 from the oneAPI repository, and the newer drivers from Intel's graphics PPA.

./setup.sh --packages        # the package line this PC asks for
./setup.sh                   # installs the first time; then it starts directly
./update.sh                  # engine, Python packages and settings (does not start the model)
./setup.sh --license free    # free software only (Intel and AMD)
  • Ubuntu 24.04 ships an old Intel driver: setup points at Intel's graphics PPA and will not start until it is updated (--old-driver starts anyway). Compute-runtime 26.35 and IGC 2.41 ended up installed here.
  • CMake rejects icpx: the contrib-icpx mode was retired on 15 October 2026. The default mode is contrib-llvm, which uses oneMKL (not free software).
  • The engine is stored in engine/ with BUILD.json ("backend": "xe" and the compiler it was built with). An engine without that record is rebuilt, and so is one whose compiler changed.
  • The model's data goes to XeStrata-data, next to the project folder; the xestrata-<model>.json configs and the logs stay in the project.
  • From the source the terminal chat is .venv/bin/python chat.py and the service is launched with serve/server.py --engine strata --config <config>.json --port 8095, which is what this deployment's start script does.

Quantizations

The choice is size, not a different model

All of them are the same Qwen3.8-Flash-Next compressed another way, or a tuned variant. Other projects make the weights: Qwen publishes the original, ISTA-DASLab compresses it, agentionai makes the Gyro ones, Unsloth the 4-to-8-bit ones.

Start-up

What the engine does before it answers

The first time it takes longer because it copies the experts into RAM and fills the card's cache. The program's own warning says the PC may respond badly for 1–3 minutes: that is normal and the window should not be closed.

  1. 01

    It probes the card and the link

    22.2 GiB of VRAM free at the start, 160 compute units, the dense prefill products in oneMKL and the rest in its own kernels with XMX. It measures the PCIe (13.2 GB/s) and lowers pcie_frac from 0.55 to 0.36 because the link is slow for this CPU.

  2. 02

    It sizes the expert cache

    16.26 GiB free minus the 2048 MiB reserved and 292 MiB for the draft head: 14,294 slots, 13.97 GiB of VRAM. It fills them from an expert profile in 24.6 s at 610 MB/s.

  3. 03

    It copies into RAM what does not fit

    A budget of 13.10 GiB: 10,282 experts ordered by the profile, copied layer by layer (8/48 at 5 s, 48/48 at 23 s), resident but not pinned (pinned 0.00 GiB). The rest are read from the GGUF.

  4. 04

    It reserves the conversation cache

    2048 MiB taken from the free RAM, for up to 4 parked conversations. With everything loaded 2,253 MiB of VRAM is left free, and that is where the MTP head fits (839 MiB).

  5. 05

    A warning that only appears on this PC

    The desktop session sets a real-time CPU limit (RLIMIT_RTTIME 200000 µs) and rtkit is not installed here: Linux can kill the process with signal 9 for no visible reason. Outside those limits it is started with systemd-run.

xestrata                      # starts whatever --setup left configured
xestrata chat                 # terminal chat (/think low, /image <path>)
xestrata --calibrate          # recalibrates the engine's values (about 15-30 min)
xestrata --bench              # speed on this PC (about 40 min); writes records/
systemd-run --user --collect -p LimitRTTIME=infinity -- xestrata
# from the source, as this deployment uses it:
.venv/bin/python serve/server.py --engine strata \
  --config xestrata-gyro-gyro-s.json --port 8095

API

How a client connects

As an “OpenAI-compatible” provider with the base URL http://127.0.0.1:8095/v1: any API key and any model name work. For Anthropic clients, /v1/messages.

The server's endpoints and what each one is for
EndpointWhat it is for
/v1/chat/completionsOpenAI: answers, streaming, tools, response_format with strict json_schema
/v1/messagesAnthropic; /v1/messages/count_tokens tokenizes a request without generating
/v1/responsesThe Responses API, the one Codex CLI uses
/v1/modelsLists the loaded model; any name sent is accepted
/healthThe thinking levels supported (default high) and the engine's state
/metricsGlobal counters, expert cache hit rate, hardware; ?requests=all reads the buffer of 500 requests
/metrics/prometheusThe same counters in Prometheus format
/v1/vram, /v1/load, /v1/unloadGive VRAM back to other programs, load or unload the model
How the thinking level is asked for in each dialect
DialectHow it is chosen
OpenAI"reasoning_effort": "none" | "low" | "medium" | "high", or "reasoning": {"effort": ...}, or "chat_template_kwargs": {"enable_thinking": false}
Anthropic"output_config": {"effort": ...}, "thinking": {"type": "disabled"}, "thinking": {"type": "enabled", "budget_tokens": N} (under 2K is low, under 8K medium, more high), or "type": "adaptive"
Nothing askedThe model's own level, high. In xestrata-<model>.json the level for every request can be set
Hard budget"reasoning_budget_tokens": N cuts the thinking at N tokens and the model answers from there; the server leaves room for the answer when the client sends max_tokens of 1,024 or more
 
curl http://127.0.0.1:8095/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-flash-next-gyro-gyro-s",
       "messages":[{"role":"user","content":"summarize this in 3 sentences"}],
       "reasoning_effort":"low","stream":true}'

curl http://127.0.0.1:8095/v1/messages \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-flash-next-gyro-gyro-s","max_tokens":1024,
       "messages":[{"role":"user","content":"hello"}],
       "thinking":{"type":"disabled"}}'

curl http://127.0.0.1:8095/health
curl 'http://127.0.0.1:8095/metrics?requests=all'
  • One request at a time (batch_slots: 0). Several at once are opt-in with "parallel": 2, and on this PC they barely scale: 1.22× with 2 requests and 1.06× with 4.
  • The first message of a conversation is read in full; after that the engine keeps the cache and reads only what is new, so the next turns start in about 140 ms instead of about 11,300 ms.
  • To use it from a phone or another machine: xestrata --host 0.0.0.0 --api-key <secret> and the address the server window prints.
  • A prompt that repeats a block is cut by the loop guard (transcribed from Project Maya); the counters appear in /metrics under loop_guard.

Failures

When something breaks, and what this PC does

  • It refuses a VRAM allocation (alloc_device: ... refused): Intel's driver can refuse allocations when the VRAM is free. The engine retries in smaller pieces and starts with what it gets; if the card ends up like that, only rebooting the PC recovers it. A newer driver avoids it.
  • Port 8095 occupied: almost always XeStrata is already running. If another program uses it, xestrata --port 8081.
  • Old driver or IGC: setup says so and shows the command. On Ubuntu 24.04 the route is the kobuk-team/intel-graphics PPA with the HWE kernel.
  • XMX unavailable: the compiler cannot use that GPU's matrix engines. Without them it runs, but the prefill takes about 1.6 times longer.
  • “the engine stopped unexpectedly”: almost always insufficient RAM. Resend the message: the engine starts on its own. If it repeats, close programs or pick a smaller quantization.
  • The prompt exceeds the context: the conversation is longer than the context chosen. New conversation or xestrata --setup with a larger one, knowing that raising the context takes VRAM away from the expert cache: from 32,768 to 131,072 the cache goes from 13.97 GiB to 11.1 GiB.
  • structured_output_failed: with thinking active and a short budget, strict json_schema does not come out. In gyro-bench the budget is 400 tokens per case.
  • Signal 9 for no visible reason: the desktop session's real-time limit (RLIMIT_RTTIME) without rtkit installed. Start with systemd-run --user --collect -p LimitRTTIME=infinity -- xestrata.

Scope

What is measured and what is only documented

Measured on this PC

  • One quantization (TQ1_0 Gyro-S), one card (Arc Pro B60), one installation route (from the source).
  • The first-start timings are from 11 November 2026 with a 32,768 context; the deployment used for the tests runs 131,072.
  • The live server state comes from /metrics of the running process while this page was being written.

Only documented, not tested here

  • The deb/rpm packages, Podman and the Windows 7z.
  • The other quantizations in the table, and AMD or NVIDIA GPUs.
  • Image generation and the multi-GPU mode.
  • Sustained or multi-user performance: one request at a time.
