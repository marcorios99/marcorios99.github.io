FormVision

Template-driven form processing with QR, OMR, OCR, and ICR.

A public synthetic, privacy-safe demo. The project is feature-complete for its portfolio scope, not a production benchmark.

From problem to output

Repeated capture, turned into reviewable results

  1. 01

    Problem

    Structured scanned forms require repetitive transcription, review, and validation before their data can be used.

  2. 02

    Solution

    An explicit layout defines each known field's geometry; when alignment is enabled, a reference image preserves it through processing.

  3. 03

    Result

    The pipeline returns a validated FormProcessingResult that can be exported to JSON, CSV, or SQLite.

Pipeline

Two image contracts, one structured result

QR and fields deliberately follow different paths: QR preserves the complete aligned page, while fields are extracted from ROIs on the cleaned image.

  1. 01

    Input and alignment

    image path → ImageLoader → optional reference alignment → aligned.

  2. 02

    Two branches

    aligned → full-page QR. MagentaDropout → cleaned → layout-defined ROIs.

  3. 03

    Extraction

    ROIs from cleaned are dispatched to OMR, ICR, or OCR according to field type.

  4. 04

    Validation and export

    Validators produce FormProcessingResult, available through JSON, CSV, or SQLite exporters.

Template and layout

Explicit geometry instead of universal detection

The public synthetic_omr_v1 template is 1240 × 1754 and defines 12 fields: 8 OMR, 1 ICR, and 3 OCR. layout.json declares page_size, ROIs, validators, and OMR options.

{
  "template_id": "synthetic_omr_v1",
  "page_size": { "width": 1240, "height": 1754 },
  "fields": [{
    "id": "question_01",
    "type": "omr",
    "roi": { "x": 157, "y": 560, "width": 268, "height": 54 },
    "options": ["A", "B", "C", "D"]
  }]
}

layout_viewer.html moves and resizes existing ROIs and saves the layout as JSON; it does not automatically detect fields.

Engines

Every data type has an explicit scope

QR

OpenCV

cv2.QRCodeDetector reads the complete aligned page. QR is neither an ROI nor a layout field.

OMR

Configured marks

Otsu thresholding scores central regions from declared options; it is deliberately simple and specific to configured geometry.

OCR

Pretrained docTR

The adapter receives an ROI and uses pretrained weights. First use can need a network download; there is no local OCR training.

ICR

MNIST references

Separated digits are classified against the included reference bank with nearest neighbors and weighted voting. It is not a trained neural network.

Architecture

A reusable Core, separate preparation and evaluation

formvision/ does not depend on demo, synthetic, training, or tools. That boundary keeps the Core focused on loading, aligning, extracting, validating, and exporting.

Public demo

Reproducible without private data

The prepared demo uses ten synthetic scans, ground truth per form, and the included ICR artifact. Forms, identities, and answers are synthetic or public.

python -m pip install -e ".[full]"
python demo.py
  • The prepared demo does not download MNIST or run the trainer.
  • docTR can download pretrained weights on first use.
  • The batch writes data/outputs/demo/report.json.

Evaluation

A JSON batch report, not a production claim

Schema 2.0 records processed forms, errors, per-field comparisons, and per-engine aggregates, including accuracy and coverage where applicable.

  • A completed batch means processing and evaluation finished; it does not mean perfect accuracy.
  • There is no production quality gate or HTML report.
  • The demo demonstrates integration and reproducibility, not production benchmarking.

Technical criteria

Decisions that make the contract explicit

01

Synthetic, reproducible assets

Reason
Publish a verifiable demo without exposing private forms, rules, or identities.
Trade-off
Synthetic variance does not measure production performance.
02

Reference, ROIs, and separate QR

Reason
Preserve known geometry and make each stage's input unambiguous.
Trade-off
The layout is part of the contract; when alignment is enabled, a reference image is required.
03

Optional engines and evaluation outside the Core

Reason
QR/OMR remain lightweight while OCR/ICR and evaluation keep explicit contracts.
Trade-off
docTR can require installation and weight downloads; the ICR artifact is distributed to avoid rebuilding it.

Limits

An intentionally bounded scope

Real limitations

  • Structured, controlled forms only.
  • The layout is part of the contract; when alignment is enabled, a reference image is required.
  • ICR supports separated digits, not cursive or touching digits.
  • OCR is pretrained and OMR is simple and layout-specific.

Non-goals

  • Arbitrary documents, PDF support, and automatic field detection.
  • HTML reports or intermediate-stage visualization.
  • Production-accuracy claims.
  • An active production roadmap: the project is feature-complete for its portfolio scope.
