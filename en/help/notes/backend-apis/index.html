Review note

Backend & APIs

An API is not just a set of routes: it is a contract between clients and the server. Explaining it well requires understanding resources, HTTP methods, status codes, validation, authentication, and authorization. In internal systems, a clear API reduces ambiguity and makes services easier to operate, debug, and evolve.

REST and resources

REST usually models a system around resources: users, documents, orders, files, or reports. HTTP methods describe the intent: GET retrieves, POST creates or triggers an operation, PUT/PATCH updates, and DELETE removes. The important thing is not memorising pretty routes, but keeping the contract consistent for API consumers.

Idempotency

An idempotent operation can be repeated without changing the final result beyond its first execution. This is vital in internal APIs because retries, timeouts, and jobs may send a request again. For example, retrieving with GET should be idempotent; creating with POST is not always idempotent unless a business key or idempotency key is used.

HTTP status codes

HTTP status codes communicate the outcome without relying only on a message. 200 indicates success, 201 creation, 400 a bad request, 401 missing authentication, 403 missing permissions, 404 a missing resource, 409 a conflict, and 422 semantically invalid data. Using them well lets web, mobile, and script clients react correctly.

JWT and security

A JWT carries signed claims such as a user, expiry, or audience. It lets a backend verify identity and permissions without looking up a session on every request, but it should not be used to store sensitive information. A signature protects integrity; it does not make token contents private when a client can read them.

Typical questions

  • When would you use 400, 401, 403, 404, 409, and 422?
  • What is the difference between authentication and authorization?
  • What makes an endpoint idempotent?
  • What information would you put, and not put, inside a JWT?
