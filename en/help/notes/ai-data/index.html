Review note

AI applied to data

For business queries, an LLM should help interpret a user’s intent, not have unrestricted access to execute SQL. A safer architecture turns natural language into structured JSON, validates it against an allowed catalogue, and only then builds controlled queries.

LLM as interpreter, not executor

An LLM is good at interpreting natural language, but it should not be free to execute SQL generated from text. In a safer architecture, the model returns structured intent and the backend decides which queries are allowed.

Intent JSON

Intent JSON can contain a metric, filters, date range, grouping, order, and output format. It turns an ambiguous question into a structure that can be validated. If JSON does not meet the schema or requests forbidden fields, it is rejected or clarification is requested.

Controlled queries

A query should be built from controlled rules, templates, or query builders. This reduces SQL injection risk, prevents access to sensitive tables, and makes it possible to audit which question generated which query. The LLM should not freely choose tables, joins, or unsafe functions.

Usable output

A good response separates data, explanation, and visualisation. The backend can return a table, summary, and metadata; the client decides whether to show text, a chart, or detail. This makes AI an interface over trusted data rather than a black box.

Typical questions

  • Why should an LLM not generate and execute SQL directly?
  • What should intent JSON contain?
  • How would you limit allowed metrics, tables, and filters?
  • How would you audit a query made from natural language?
