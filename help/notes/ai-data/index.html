Nota de repaso

IA aplicada a datos

Para consultas empresariales, el LLM deberia ayudar a interpretar la intencion del usuario, no tener acceso libre a ejecutar SQL. Una arquitectura mas segura es convertir lenguaje natural en JSON estructurado, validar ese JSON contra un catalogo permitido y recien despues construir consultas controladas.

LLM como interprete, no como ejecutor

Un LLM es bueno interpretando lenguaje natural, pero no deberia tener libertad para ejecutar SQL generado por texto. En una arquitectura mas segura, el modelo devuelve una intencion estructurada y el backend decide que consultas estan permitidas.

JSON de intencion

El JSON de intencion puede contener metrica, filtros, rango de fechas, agrupacion, orden y formato de salida. Esto transforma una pregunta ambigua en una estructura validable. Si el JSON no cumple el esquema o pide campos no permitidos, se rechaza o se solicita aclaracion.

Consultas controladas

La consulta debe construirse desde reglas, plantillas o query builders controlados. Eso reduce riesgo de SQL injection, evita consultar tablas sensibles y permite auditar que pregunta genero que consulta. El LLM no debe decidir libremente tablas, joins o funciones peligrosas.

Salida usable

Una buena respuesta separa datos, explicacion y visualizacion. El backend puede devolver tabla, resumen y metadatos; el cliente decide si mostrar texto, grafico o detalle. Esto hace que la IA sea una interfaz sobre datos confiables, no una caja negra.

Preguntas tipicas

  • Por que no conviene dejar que el LLM genere y ejecute SQL directamente?
  • Que deberia contener un JSON de intencion?
  • Como limitarias metricas, tablas y filtros permitidos?
  • Como auditarias una consulta hecha desde lenguaje natural?
