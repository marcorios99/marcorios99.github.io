Nota de repaso

Backend & APIs

Una API no es solo un conjunto de rutas: es un contrato entre clientes y servidor. Para explicarla bien conviene dominar recursos, metodos HTTP, codigos de estado, validacion, autenticacion y autorizacion. En sistemas internos, una API clara reduce ambiguedad y hace mas facil operar, depurar y evolucionar servicios.

REST y recursos

REST suele modelar el sistema alrededor de recursos: usuarios, documentos, ordenes, archivos o reportes. Los metodos HTTP describen la intencion: GET consulta, POST crea o dispara una operacion, PUT/PATCH actualizan y DELETE elimina. Lo importante no es memorizar rutas bonitas, sino que el contrato sea consistente para quien consume la API.

Idempotencia

Una operacion idempotente puede repetirse sin cambiar el resultado final mas alla de la primera ejecucion. Esto es clave en APIs internas porque hay reintentos, timeouts y jobs que pueden volver a enviar una solicitud. Por ejemplo, consultar con GET deberia ser idempotente; crear con POST no siempre lo es, salvo que uses una clave de negocio o idempotency key.

Codigos HTTP

Los codigos HTTP comunican el resultado sin depender solo del mensaje. 200 indica exito, 201 creacion, 400 error de solicitud, 401 falta de autenticacion, 403 falta de permisos, 404 recurso no encontrado, 409 conflicto y 422 datos semanticamente invalidos. Usarlos bien hace que clientes web, moviles y scripts puedan reaccionar correctamente.

JWT y seguridad

Un JWT transporta claims firmados, como usuario, expiracion o audiencia. Sirve para que el backend verifique identidad y permisos sin consultar una sesion en cada request, pero no debe usarse como lugar para guardar informacion sensible. La firma protege integridad, no convierte el contenido en privado si el token puede ser leido por el cliente.
